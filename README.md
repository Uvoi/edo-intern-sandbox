# ЭДО Песочница

Учебный проект для стажёра на стеке и архитектуре Astral.Frontend. Основа — шаблон `project-starter` (`cold-start`). Бэкенда нет: все данные отдаёт stub в `api/fakers` (подход Contract First).

Гайды: https://guides.frontend.cloud.astral-dev.ru  
UI-kit: https://www.npmjs.com/package/@astral/ui (там же ссылка на Storybook)

## Запуск

Нужны Node.js ≥ 22 и pnpm ≥ 12 (`npm i -g pnpm` или `corepack enable pnpm`). Через npm проект ставиться не будет: в `package.json` это запрещено полем `devEngines`.

```bash
pnpm install
pnpm dev           # http://localhost:3001
```

Настройки pnpm (overrides, allowBuilds) лежат в `pnpm-workspace.yaml`, как в `project-starter`.

| Команда | Что делает |
|---|---|
| `pnpm dev` | dev-сервер |
| `pnpm tests` | unit-тесты (vitest) |
| `pnpm lint` | biome с автоисправлением |
| `pnpm lint:types` | проверка типов |
| `pnpm check` | всё сразу — **должно проходить перед каждым MR** |
| `pnpm unused-exports:check` | knip, поиск мёртвого кода |
| `pnpm analyze-es-deps:circular` | поиск циклических зависимостей |

## Что уже есть

```
application/   app.tsx, routes.tsx, pages/            — роутинг и инициализация
screens/       Example, CounterpartyList, NotFound    — экраны
modules/       layout, identity, counterparty         — бизнес-модули
api/           _endpoints, dto, fetchers, fakers, services
shared/        proxy-файлы @astral/ui, сервисы, утилиты, тестовые хелперы
```

- **Эталон — модуль `counterparty`** и раздел «Контрагенты». Есть чтение списка и работающий пример **«В архив / Восстановить»**: действия строки → подтверждение → mutation → pending → уведомление → инвалидация, с тестами и DI renderer. Маршрут чтения и ручные сценарии — в [`modules/counterparty/README.md`](modules/counterparty/README.md). Строка «ООО Учебная ошибка архивации» показывает отказ сервера. Реализацию `document` дополняет стажёр самостоятельно.
- **API документов готово**, писать его не нужно:
  - DTO: `api/dto/document`;
  - fetcher: `api/fetchers/document.ts`;
  - fakers: `api/fakers/document.ts` — для тестов.

  Fetcher содержит:
  - `infiniteQueries.documentList` — список с фильтрами `search`, `status`, `counterpartyId`, сортировкой `sortField`/`sortOrder` и пагинацией;
  - `queries.documentStatistics` — количество документов по статусам с учётом `search` и `counterpartyId`;
  - `mutations.createDocument` и `mutations.deleteDocument`;
  - список контрагентов для фильтра и формы — `api/fetchers/counterparty.ts`.
- **Stub ведёт себя как сервер.** Он хранит данные в памяти до перезагрузки страницы, честно фильтрует, сортирует и пагинирует, а созданный документ появляется в начале списка. Отвечает с задержкой около 0,8 с. Ошибки:
  - наименование документа содержит слово «ошибка» → сервер отвечает ошибкой создания;
  - удалить можно только документ в статусе `Draft`, иначе — ошибка.

## Задание: раздел «Документы»

Нужно сделать модуль `document` из нескольких фич и собрать из них экран `DocumentListScreen` на маршруте `/documents` с пунктом «Документы» в меню.

### Фичи

1. **`DocumentList`** — таблица (`DataGridInfinite`) с бесконечной прокруткой. Колонки:
   - номер;
   - наименование;
   - контрагент — наименование и ИНН;
   - сумма — в формате `1 234 567,89 ₽` (в API сумма в копейках);
   - статус — `Tag` с цветом и русским названием;
   - дата создания — `ДД.ММ.ГГГГ`.

   Сортировка по наименованию, сумме и дате хранится в search params.
2. **`DocumentFilters`** — поиск по наименованию или номеру, выбор статуса и выбор контрагента. Значения хранятся в search params: после перезагрузки страницы фильтры сохраняются, ссылку можно отправить. Есть кнопка «Сбросить».
3. **`DocumentStatistics`** — плашки «Черновик: 12», «Отправлен: 30»… с учётом текущего поиска и контрагента. Клик по плашке выставляет фильтр по этому статусу, повторный клик снимает его.
4. **`CreationDocumentForm`** — модальное окно создания документа, react-hook-form + `@astral/validations`. Поля:
   - наименование — обязательно, до 200 символов;
   - тип — обязательно;
   - контрагент — обязательно;
   - сумма в рублях — обязательно, больше 0, до двух знаков после запятой.

   При успехе: уведомление «Документ создан», список и статистика обновляются, окно закрывается. При ошибке: уведомление с текстом от сервера, окно остаётся открытым.
5. **Экран `DocumentListScreen`.** Заголовок «Документы», кнопка «Создать документ», под ней фильтры и статистика, ниже таблица. Связь фич между собой (общие фильтры, открытие и закрытие формы) — в интеграционном `UIStore` экрана или через общий store в `domain`. Фичи напрямую друг о друге не знают.

### Дополнительно (по желанию)
6. **Удаление черновика.** В строке таблицы — действие «Удалить», только для `Draft`; правило «удалять можно только черновик» живёт в `domain`. Перед удалением — подтверждение (`ConfirmDialog`), после удаления — обновление списка и статистики.
7. **Пустые состояния.** «Документов пока нет» и «Ничего не найдено, измените фильтры» — это разные тексты.

### Обязательные тесты
- `domain`: форматирование суммы, перевод рублей в копейки, словарь статусов (если в нём есть логика), store фильтров.
- `UIStore` фич: с какими параметрами запрашивается список; клик по статистике меняет фильтр; успешное создание (уведомление, инвалидация, закрытие) и ошибка создания.
- Валидация формы через `renderHook` (только логика, без UI).

### Как сдавать
Работа идёт этапами. **Каждый этап — отдельная ветка и merge request** на ревью наставнику.

| Этап | Что входит |
|---|---|
| 1 | `domain` (словари, форматтеры, store фильтров) + `DocumentList` + page, маршрут, пункт меню |
| 2 | `DocumentFilters` + сортировка |
| 3 | `DocumentStatistics` + интеграция на экране |
| 4 | `CreationDocumentForm` |
| 5* | удаление черновика, пустые состояния |

- Ветка: `DOC-<номер этапа>/<кратко>`. Коммиты в стиле conventional commits: `feat(DOC-1): добавлен список документов`.
- Перед MR `pnpm check` проходит без ошибок. В описании MR — что сделано и что не успел.

### Критерии приёмки
- Слои и зависимости по [архитектуре](https://guides.frontend.cloud.astral-dev.ru/docs/arch/overview): компонент только рендерит, вся логика — в `UIStore` или `useLogic`, данные — только через fetchers.
- Сторонние библиотеки подключаются только через proxy-файлы в `shared`, в корнях слоёв и сегментов нет `index.ts`.
- Нейминг по [style guide](https://guides.frontend.cloud.astral-dev.ru/docs/style-guide/rules/naming): `List` вместо `s`, `is/has`, `handle*`/`on*`, `*Store`, UPPER_CASE для констант модуля, kebab-case для URL.
- Mutation создаётся в конструкторе. После изменений вызывается `invalidate`, кэш руками не правится.
- Тесты по [гайду](https://guides.frontend.cloud.astral-dev.ru/docs/unit-testing/overview): `it`, `sut`, `setup()` в каждом тесте, `mock`/`mockFetcher`, без `vi.mock`, названия «Предмет + результат + условие».

## Если ты знаешь FSD

Идеи похожие, но названия и границы отличаются:

| FSD | Astral Architecture |
|---|---|
| `app` | `application` (+ `application/pages` — только роутинг и guards) |
| `pages` | `screens` — экран **не знает** о роутинге |
| `widgets` | отдельного слоя нет: композиция фич — в `screens` |
| `features` | `modules/<module>/features` — готовый UI-компонент со своей логикой |
| `entities` | `modules/<module>/domain` — бизнес-логика без UI |
| `shared/api` | отдельный слой `api`: `_endpoints`, `dto`, `fetchers`, `fakers` |
| `model` (redux/effector) | MobX `UIStore` с DI и фабрикой `createUIStore` |
| public API слайса (`index.ts`) | `index.ts` только в директории конкретной сущности; barrel-файлы в корнях запрещены |
| запрет cross-import, `@x` | модули импортируют `features`/`domain` друг друга напрямую; приватное — с префиксом `_` |
